# Publish on a docs site

The tools on this site produce HTML pages, and md-iframe embeds them in an MkDocs or Zensical site. Rather than committing generated pages, it is usually better to generate them during the build: keep only the sources in the repository, and let CI produce the HTML on every deploy. This site is built exactly this way.

The example below uses PinConnect, 3DStep, WebFlash and GitHub Pages; the pattern is the same for any tool and any host.

## Lay out the sources

Keep one folder per board, holding its TOML and its image. CI writes `<board>.pinout.html` beside each TOML, exactly where the embed tag on your page points:

```
docs/
├── boards.md
└── pinouts/
    └── board/
        ├── board.toml            ← committed
        ├── board.png             ← committed
        └── board.pinout.html     ← generated by CI, not committed
```

The page embeds the generated file:

```markdown
![Board pinout](pinouts/board/board.pinout.html){ type=iframe }
```

3DStep pages work the same way, with one folder per page holding its project and the GLB files of its models. CI writes `<name>.3dstep.html` beside each project:

```
docs/
├── assembly.md
└── 3d/
    └── fan/
        ├── fan.toml              ← committed
        ├── board.glb             ← committed
        ├── fan.glb               ← committed
        └── fan.3dstep.html       ← generated by CI, not committed
```

```markdown
![Mount the fan](3d/fan/fan.3dstep.html){ type=iframe }
```

WebFlash cards work the same way too, with one folder per board holding its board TOML and the files it names: the photo, and for a prebuilt board the firmware file. CI writes `<board>.webflash.html` beside each TOML:

```
docs/
├── flashing.md
└── firmware/
    └── board/
        ├── board.toml            ← committed
        ├── board.png             ← committed
        └── board.webflash.html   ← generated by CI, not committed
```

```markdown
![Flash Klipper to the board](firmware/board/board.webflash.html){ type=iframe }
```

Ignore the generated files so they never get committed by accident:

```gitignore
docs/pinouts/**/*.pinout.html
docs/3d/**/*.3dstep.html
docs/firmware/**/*.webflash.html
```

## Enable md-iframe

In `mkdocs.yml`, beside `attr_list`:

```yaml
markdown_extensions:
  - attr_list
  - md_iframe
```

## Generate in the workflow

Add these steps to your workflow before `mkdocs gh-deploy` or `zensical build`:

```yaml
      - run: pip install "git+https://github.com/xbst/PinConnect.git@master"
      - run: pip install "git+https://github.com/xbst/md-iframe.git@master"
      - name: Generate interactive pinouts
        run: |
          shopt -s nullglob
          for toml in docs/pinouts/*/*.toml; do
            echo "pinconnect $toml"
            pinconnect "$toml" -i
          done
```

`-i` embeds the board image into the HTML, so the built site does not depend on the image path resolving. `shopt -s nullglob` keeps the loop quiet when a folder has no TOML yet.

For 3DStep pages, add:

```yaml
      - run: pip install "git+https://github.com/xbst/3DStep.git@master"
      - name: Generate 3D assembly instructions
        run: |
          shopt -s nullglob
          for toml in docs/3d/*/*.toml; do
            echo "3dstep $toml"
            3dstep "$toml"
          done
```

A 3DStep page always carries its models inside it, so the loop needs no flag.

For WebFlash cards, add:

```yaml
      - run: pip install "git+https://github.com/xbst/webflash.git@master"
      - name: Generate firmware flashing cards
        run: |
          shopt -s nullglob
          for toml in docs/firmware/*/*.toml; do
            echo "webflash $toml"
            webflash "$toml" -i
          done
```

`-i` inlines the board photo, and a `[prebuilt]` board's firmware file, into the page. A card builds the firmware in the reader's browser with the runtime it loads from [webflash.isiks.tech](https://webflash.isiks.tech), so the job only renders the pages: it builds no firmware. See [Embedding a card](../webflash/embedding.md). A repository that keeps only the STEP files can convert them in the same job, before the loop, with the `step` extra; see [Convert a STEP file](../3dstep/command-line.md#convert-a-step-file) for why committing the GLB files the designer wrote is usually the better choice.

!!! tip "Install from `master` rather than pinning a release"
    Each deploy then regenerates your pages with the current version of the tools, so fixes and new features in the generated page, such as tooltip behavior, theming, accessibility and the mobile layout, reach your published site automatically.

## A complete workflow

This is a whole GitHub Pages workflow for a Zensical site, the one this site uses. Save it as `.github/workflows/ci.yml`, and set the repository's Pages source to **GitHub Actions**:

```yaml
name: ci
on:
  push:
    branches:
      - master
      - main
permissions:
  contents: read
  pages: write
  id-token: write
jobs:
  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/configure-pages@v6
      - uses: actions/checkout@v7
      - uses: actions/setup-python@v6
        with:
          python-version: 3.x
      - run: pip install zensical
      - run: pip install "git+https://github.com/xbst/PinConnect.git@master"
      - run: pip install "git+https://github.com/xbst/3DStep.git@master"
      - run: pip install "git+https://github.com/xbst/webflash.git@master"
      - run: pip install "git+https://github.com/xbst/md-iframe.git@master"
      - name: Generate interactive pinouts
        run: |
          shopt -s nullglob
          for toml in docs/pinouts/*/*.toml; do
            echo "pinconnect $toml"
            pinconnect "$toml" -i
          done
      - name: Generate 3D assembly instructions
        run: |
          shopt -s nullglob
          for toml in docs/3d/*/*.toml; do
            echo "3dstep $toml"
            3dstep "$toml"
          done
      - name: Generate firmware flashing cards
        run: |
          shopt -s nullglob
          for toml in docs/firmware/*/*.toml; do
            echo "webflash $toml"
            webflash "$toml" -i
          done
      - run: zensical build --clean
      - uses: actions/upload-pages-artifact@v5
        with:
          path: site
      - uses: actions/deploy-pages@v5
        id: deployment
```

Leave out the steps of a tool you do not use. For MkDocs, install `mkdocs-material` instead of `zensical`, and run `mkdocs build` in place of `zensical build --clean`.

## Build locally

Run the same steps on your machine to preview the site. In a virtual environment with the same packages installed:

**PowerShell**

```powershell
Get-ChildItem docs/pinouts/*/*.toml | ForEach-Object { pinconnect $_.FullName -i }
Get-ChildItem docs/3d/*/*.toml | ForEach-Object { 3dstep $_.FullName }
Get-ChildItem docs/firmware/*/*.toml | ForEach-Object { webflash $_.FullName -i }
zensical serve
```

**Linux / macOS**

```bash
for toml in docs/pinouts/*/*.toml; do pinconnect "$toml" -i; done
for toml in docs/3d/*/*.toml; do 3dstep "$toml"; done
for toml in docs/firmware/*/*.toml; do webflash "$toml" -i; done
zensical serve
```

Rerun the loops after editing a TOML: the dev server rebuilds the page, but not the pinout, the 3D page or the card.

## A shared theme

A site-wide theme, matching your site's colors and fonts, can live once beside the folders, one for each tool. Each board points at it with `theme_dir`:

```toml
[board]
title = "My board"
image = "board.png"
width = 1920
height = 1080
theme = "mysite"
theme_dir = ".."
```

with the theme in `docs/pinouts/mysite.toml`. The loop above only renders `docs/pinouts/*/*.toml`, so the theme itself is never rendered as a board. This site's [OwlFC-Mini example](../pinconnect/examples/board.md) uses one; see [PinConnect themes reference](../pinconnect/reference/themes.md).

3DStep projects do the same with a 3DStep theme in `docs/3d/mysite.toml`:

```toml
[assembly]
title = "Mount the fan"
models = ["board.glb", "fan.glb"]
theme = "mysite"
theme_dir = ".."
```

WebFlash board TOMLs name a WebFlash theme in `docs/firmware/mysite.toml` the same way:

```toml
[board]
title = "My board"
image = "board.png"
theme = "mysite"
theme_dir = ".."
```

The tools' theme files have the same shape but their own tokens, so a site keeps one for each. This site's [PiCAN 2 example](../3dstep/examples/assembly.md) uses one; see [3DStep themes reference](../3dstep/reference/themes.md#a-site-theme). Its WebFlash cards use one too; see [WebFlash themes reference](../webflash/reference/themes.md). The 3DStep designer cannot read the folder, so open the site theme's `.toml` together with a project to work on it there; its Generate then gives the page the loop renders.
